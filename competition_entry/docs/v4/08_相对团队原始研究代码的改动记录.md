原始研究代码回答的是一个**效用问题**：目标服务器只拿到各源服务器已有的 LDP Top-m 摘要（品类、频率估计、方差），外加可选的公开目标上下文，能否预测目标自己的 Top-k？它比较了直接平均、方差加权、截断感知（censor-aware）、上下文加权、两阶段迁移等融合方法。它在 Amazon Books、Yelp 六城市和模拟数据上验证。

PrivEdge 回答的是一个**安全问题**：在同样的数据流上，如果有人伪造用户、攻破一个区域、篡改或重放摘要、冒用身份、代扣隐私预算，预测还能不能信？所以 PrivEdge 把原始融合算法当作"内核"，在它外面加了发布端过滤、签名、账本、网关、鲁棒融合和三态决策。

## 3 重新实现的部分（数学相同，接口不同）

### 3.1 OLH 本地差分隐私：`privedge/privedge/ldp.py`

| 方面 | 原始 `ldp_protocols.olh` | PrivEdge `ldp.py` |
|---|---|---|
| 结构 | 一个函数完成扰动 + 估计 | 拆成用户端 `perturb()`（输出每个用户的 (种子, 桶) 对）和发布端 `aggregate()` |
| 参数 | g = round(e^ε)+1，p = e^ε/(e^ε+g−1)，q = 1/g | 相同 |
| 随机数消耗顺序 | 先抽 n 个种子，再逐个用户抽扰动 | **相同**（这是逐位一致的前提） |
| 方差 | `_plugin_variance`（频率先截到 [0, n]） | 相同公式 |
| 支持计数 | 逐用户循环 | 分块向量化（`support_matrix`），结果相同、速度快很多 |
| 哈希 | **装了 xxhash 就用 xxhash32，没装才用 splitmix64 备用哈希** | **固定使用 splitmix64 备用哈希**（`HASH_FAMILY = "splitmix64-fallback-v1"`，写进每份摘要信封） |
| 其他机制 | GRR、OUE、OLH、PEM | 只有 OLH |

为什么要拆开：PrivEdge 需要"用户报告"这个中间产物。发布端过滤要看每条报告支持哪些品类，攻击模块要往里面混入伪造报告。原始函数直接返回估计值，拿不到报告。

**哈希差异的后果**：原始代码的环境记录（`ENVIRONMENT.txt`）显示当时装了 xxhash 4.0.1，所以原始 `outputs/` 里的历史数字（例如 Yelp 六城市 Recall 0.417/0.457、0.663/0.673）是用 xxhash 跑出来的。PrivEdge 的虚拟环境没有装 xxhash。因此：

- "逐位一致"指的是：**在不装 xxhash 的同一环境下**，PrivEdge 与原始代码输出相同。单元测试是在 PrivEdge 虚拟环境（无 xxhash）中核对的。E1 对照的是本工作区 Olist 数据审计（Gate E）时用原始代码生成的记录，120 行最大差值为 0，说明那批记录也是用备用哈希生成的。
- PrivEdge 的数字**不能**和原始 `outputs/` 里的历史数字逐位比较。两种哈希在统计上等价，但同一种子下的随机结果不同。
- 报告里已注明"哈希族为 splitmix64 备用实现"。

### 3.2 发布摘要的生成：`privedge/privedge/pipeline.py::summarize_reports`

与原始 `experiment.py::_release` 的 OLH 分支一致：按估计值取 Top-m，频率 = max(0, 计数)/n，方差 = 方差/n²，另外多记一个 `tail_bound`（第 m+1 名的频率）。区别是 PrivEdge 在估计之前可以先跑发布端过滤（第 4 节），并把结果装进签名信封，而不是直接构造 `ServerRelease`。

### 3.3 数据：`privedge/privedge/adapters/`

原始代码的数据解析器针对 Amazon Books 与 Yelp（`prepare_data.py`、`experiments/validation/*`）。PrivEdge 不再使用这两套数据，改为三个新的导出脚本，统一输出 `domain.json` + `private_events.csv.gz`（+ 可选 `public_context.csv`）：

| 脚本 | 数据 | 作品中的角色 |
|---|---|---|
| `export_trd.py` | 美团外卖 TRD（Zenodo 8025855），北京 11 个商圈首单 | 主场景 |
| `export_olist.py` | 巴西电商 Olist，按州分区 | 跨国对照 |
| `export_massive.py` | Massive-STEPS 城市签到 | 高异质压力测试 |

每个用户只保留一个事件（与原始代码"每用户单事件"的做法一致），目标区域的真实分布只在离线评估时读取。

## 4 全新增加的部分（原始代码中没有）

| 模块 | 文件 | 作用 |
|---|---|---|
| 发布端伪造用户过滤 | `robust.py::filter_fake_reports` | 诚实 OLH 报告同时支持 k 个固定品类的概率约为 g^−k，而伪造用户（MGA）的报告会同时支持全部目标品类。先找联合支持异常高的品类对（z>6），再贪心扩展到最多 8 个，剔除同时支持这组品类的报告 |

## 5 方法与研究方向上的变化

| 方面 | 原始研究代码 | PrivEdge |
|---|---|---|
| 核心问题 | 融合方法能否更准地迁移 Top-k | 在隐私保护下，结果能否可信（抗投毒、可审计） |
| 主线融合 | 截断感知 + 公开上下文（`fuse_censor_aware_item_context`） | v1 沿用它（历史对照）；**v2 起改为不用上下文的方差加权**（`fuse_variance_weighted`），外加截尾、支持规则、权重封顶（默认 D4） |
| 公开上下文 | 主要卖点之一 | 降级为附录说明。原因：Olist 与 Massive 的 Gate D 都未通过，公开上下文没有目标特异增益；错配上下文反而使 NDCG 下降 0.116（E8） |
| 两阶段迁移、凸区间估计器、自适应选源 | 探索性模块 | 不在主线中使用 |
| 鲁棒性 | `fuse_robust_adaptive_context`：用"上下文相关度 + 同行一致度"选源，方差下限为中位数的 0.5 倍，效用上限为中位数的 3 倍；`experiment.py::_adversarial_release` 模拟"极小方差的假摘要" | 思路相近但独立实现：权重封顶对所有源生效，用**留一**中位数（被检源无法抬高自己的上限），不依赖上下文，并有定理 2 给出影响上界 |
| 攻击模型 | 只有模拟的异常源（G6：无关、过时、恶意、缺失） | 10 种攻击，分为数据投毒、被攻破发布者、网络攻击、账本攻击四类 |
| 评估纪律 | 固定配置批量实验 | 先写预注册（假设、判定规则）再运行；同一数据上不重调；确认性复验用新种子（601、709、811、907、1009）；每个运行目录带 `manifest.json`（代码指纹、环境、数据 SHA-256） |
| 数据 | Amazon Books、Yelp、模拟 | TRD（主）、Olist（对照）、Massive（压力测试） |
| 环境 | Python 3.11 + NumPy + xxhash | Python 3.12.14 + NumPy + cryptography + FastAPI 等，无 xxhash（见 `requirements.lock`） |

原始研究的一个重要结论被 PrivEdge 保留并如实沿用：**各种融合方法相对直接平均没有稳定优势**。所以 PrivEdge 不宣称"预测更准"，而是宣称"加了安全层之后几乎不损失效用，同时挡住攻击"（E9：无攻击时 NDCG 变化在 [−0.0012, +0.0198]）。

## 6 容易被问到的对照问题

1. **"原始代码的 Yelp 0.663 为什么没出现在报告里？"** 那是原始研究在 Yelp 上的探索性结果，且用的是 xxhash。PrivEdge 不使用 Yelp，报告只引用 PrivEdge 自己预注册运行的结果（E9–E19）。
2. **"PrivEdge 的 variance_weighted 和原始的是同一个吗？"** 是同一个函数（逐字节副本）。D4 的区别只在输入：先截尾，再把权重封顶后交给原始的 `_weighted_fusion`，最后只保留支持数 ≥2 的品类。
3. **"为什么不用原始的 PEM / GRR / OUE？"** 发布端过滤依赖 OLH 的"种子 + 桶"结构来计算联合支持，因此主线固定用 OLH。其他机制保留在副本中，没有实现对应的过滤。
4. **"原始代码里的 `_adversarial_release` 和 PrivEdge 的权重劫持攻击有什么关系？"** 两者都利用"谎报极小方差"。原始代码只在模拟中用它测选源稳健性；PrivEdge 把它扩展成预注册的 V3/V4 攻击（劫持 + 注入 + 扣热门），并以权重封顶防御。
